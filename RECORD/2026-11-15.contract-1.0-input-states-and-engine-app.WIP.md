## Where jgenesis-wasm stands (0.1.1)

- Legacy contract: `load(config)`, engine-specs `^0.2.4` (ROADMAP: ❌ 1.0).
- Upstream's web frontend (`frontend/jgenesis-web`, Rust + winit + wgpu), patched by
  `scripts/patch-jgenesis-web.mjs` (open a ROM from bytes). Measured on upstream `master`:
  - **no save states** on the web: `save_state` / `load_state` exist only in the native driver
    (`jgenesis-native-driver`); the web keeps cartridge saves (SRAM) in IndexedDB;
  - **no gamepads** on the web: input is winit's keyboard only, so neither a physical pad nor the
    touch pad reaches it today;
  - rendering needs **WebGPU** (in headless Chromium the software adapter panics in
    `createBuffer(mappedAtCreation)` — seen in play.germade's Mega Drive record), so this
    session cannot see it run; a real device can.

## Plan

1. **Contract 1.0** — `JgenesisSDK` / `JgenesisPlay` on engine-specs' bases, self-contained ESM,
   storage under `jgenesis/<namespace>/`; `load()` goes (minor release).
2. **Gamepads, without touching Rust** — the SDK reads `navigator.getGamepads()` each frame and
   presses jgenesis' own key bindings for each system (Genesis A B C X Y Z Mode Start; SNES;
   Game Boy…) with `KeyboardEvent`s on the element winit listens to. Physical pads and the touch
   pad then both play.
3. **Save states — a Rust patch** in `patch-jgenesis-web.mjs`: two commands on the emulator
   channel, `request_save_state()` → the emulator's bincode bytes handed to JS, and
   `request_load_state(bytes)` (the core types are already `Encode + Decode`, as the native
   driver's slots show). The SDK stores them as slots in OPFS with blastem's `play.states` shape
   and a canvas snapshot. Needs a rebuild of the wasm (the build image).
4. **The engine app** — blastem's app on this SDK (`jgn-` classes); its Escape settings overlay
   off through the app.
5. **Verify** — `make test`; the patch applies and builds; the app's menus in Chromium; the game,
   the pads and the states on a device with WebGPU (the owner's).
